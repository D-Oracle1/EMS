1. PROJECT OVERVIEW
================================================================================

System Name  : Hylink Finance Limited — Enterprise Management System
Short Name   : Hylink EMS
Version      : 2.0.0
Type         : Full-Stack Web Application (Progressive Web App)
Organization : Hylink Finance Limited
Currency     : Nigerian Naira (NGN)

DESCRIPTION
-----------
Hylink EMS is a comprehensive internal management platform for a financial
institution. It covers the complete lifecycle of lending, savings, fixed
deposits, HR operations, double-entry accounting, document archiving, field
verification, audit compliance, and role-based access control — all within
a single, unified Next.js application.

The system is designed to be:
  • Audit-ready         — every action is logged with who, what, when, and IP
  • Double-entry clean  — all financial transactions post balanced journal entries
  • Role-gated          — granular permissions per module and action
  • Offline-capable     — PWA service worker caches critical assets
  • Multi-branch        — branches, departments, and supervisory hierarchies

3. SYSTEM ARCHITECTURE
================================================================================

ARCHITECTURE STYLE
  Full-stack monolith using Next.js App Router. There is no separate API
  server. All data access goes through Next.js Server Actions (src/actions/).
  The database is accessed exclusively via Prisma ORM.

REQUEST FLOW
  Browser → Next.js Middleware (auth check, edge-compatible)
          → Next.js Server Component (data fetch)
          → Server Action (mutation / form submit)
          → Prisma → PostgreSQL

AUTHENTICATION FLOW
  1. Staff submits credentials at /login
  2. NextAuth Credentials provider verifies email + bcrypt hash
  3. Failed attempts increment counter; ≥5 failures lock account 30 min
  4. Successful login resets counter, writes audit log
  5. JWT token issued (8-hour expiry) containing:
       id, email, employeeId, firstName, lastName,
       role, roleCode, roleLevel, approvalLimit,
       department, departmentCode, branchId, branchName,
       permissions[], mustChangePassword
  6. Middleware checks JWT on every request (Edge runtime)
  7. If mustChangePassword=true, user is redirected to /change-password

MIDDLEWARE PROTECTION
  All routes except static assets and /api/auth/* are protected.
  Unauthenticated requests are redirected to /login.

PWA ARCHITECTURE
  Service worker is generated at build time by @serwist/next.
  Offline fallback page: /~offline
  Install prompt component: pwa-install-prompt.tsx

5. AUTHENTICATION & SECURITY
================================================================================

PROVIDER
  NextAuth v5 Credentials Provider
  Strategy: JWT (stateless sessions)
  Session max age: 8 hours (configurable)

PASSWORD SECURITY
  Hashing: bcryptjs
  Rounds: Configurable via BCRYPT_ROUNDS env var (default 12)
  New staff: mustChangePassword = true (forced redirect to /change-password)

BRUTE-FORCE PROTECTION
  Failed login counter per staff account.
  After 5 consecutive failures → account locked for 30 minutes.
  All failed attempts are written to the AuditLog.

ACCOUNT STATES
  A staff account must be in ACTIVE status to log in.
  INACTIVE / SUSPENDED / TERMINATED / ON_LEAVE accounts are blocked.

SESSION PAYLOAD
  The JWT token contains: id, email, employeeId, firstName, lastName,
  role, roleCode, roleLevel, approvalLimit, department, departmentCode,
  branchId, branchName, permissions[], mustChangePassword.

EDGE MIDDLEWARE
  src/middleware.ts uses the auth config (edge-compatible, no Prisma/bcrypt).
  Protects all routes matching the defined pattern.
  Static assets, service worker, and /api/auth/* are excluded from protection.

USER SESSIONS TABLE
  The UserSession model stores optional session metadata (IP, user agent,
  token, expiry) for security auditing beyond what JWT provides.

SOFT DELETES
  Staff, Customer, Loan, SavingsAccount, and Document records are soft-deleted
  (isDeleted flag + deletedAt + deletedBy) to preserve audit trail integrity.

6. ROLES & PERMISSIONS
================================================================================

ROLE MODEL
  Roles have a numeric level (higher = more authority) and an optional
  financial approvalLimit (maximum transaction amount a role can approve).

PERMISSION MODEL
  Permissions are defined as module + action combinations (e.g. LOANS:APPROVE).
  They are assigned to roles via the RolePermission junction table.

PERMISSION MODULES
  AUTH, HR, LOANS, SAVINGS, FIXED_DEPOSITS, ACCOUNTING, CUSTOMERS,
  DOCUMENTS, VERIFICATION, REPORTS, AUDIT, NOTIFICATIONS, SETTINGS, STAFF

PERMISSION ACTIONS
  CREATE, READ, UPDATE, DELETE, APPROVE, REJECT, EXPORT, PRINT, REVERSAL

EXAMPLE ROLE HIERARCHY (seeded defaults)
  SUPER_ADMIN        Level 100  — Full access, no approval limit
  EXECUTIVE          Level 90   — Read-only executive dashboard
  BRANCH_MANAGER     Level 70   — Branch operations + approval
  LOAN_MANAGER       Level 60   — Loan approval within limit
  ACCOUNTANT         Level 50   — Accounting module
  VERIFICATION_OFFICER Level 40 — Verification tasks
  LOAN_OFFICER       Level 30   — Loan creation, customer management
  TELLER             Level 20   — Savings & FD transactions
  HR_OFFICER         Level 20   — HR module
  STAFF              Level 10   — Basic access (own profile, notifications)

PERMISSION GATE COMPONENT
  <PermissionGate permission="LOANS:APPROVE"> ... </PermissionGate>
  Conditionally renders children based on session permissions array.

SIDEBAR NAVIGATION
  The sidebar is role-aware and only shows modules the user has access to.

8.3 LOAN MANAGEMENT
------------------------------------------------------------------------
Routes:  /loans              — Paginated loan list, filterable by status
         /loans/new          — New loan application form
         /loans/[id]         — Full loan detail with workflow controls

Action:  src/actions/loan.actions.ts

LOAN LIFECYCLE
  1. DRAFT           — Loan officer creates application; selects customer,
                       product, amount, tenure, purpose, collateral.
  2. PENDING_VERIFICATION — Submitted for field verification.
  3. VERIFICATION_IN_PROGRESS — Verification officer begins field visit.
  4. VERIFIED        — Field report submitted; ready for credit decision.
  5. PENDING_APPROVAL — Sent to approving authority.
  6. APPROVED        — Credit committee/manager approves.
  7. REJECTED        — Application rejected at any decision point.
  8. PENDING_DISBURSEMENT — Approved; awaiting funds transfer.
  9. DISBURSED       — Funds released; repayment schedule generated.
  10. ACTIVE         — Loan being serviced.
  11. OVERDUE        — Missed repayment(s).
  12. DEFAULTED      — Significantly overdue (as per policy).
  13. CLOSED         — Fully repaid.
  14. WRITTEN_OFF    — Bad debt write-off.

INTEREST CALCULATION
  • FLAT rate: total interest = principal × rate × (tenure/12)
    monthly instalment = (principal + total interest) / tenure
  • REDUCING BALANCE: EMI = P × r × (1+r)^n / ((1+r)^n - 1)
    where r = annual rate / 12 / 100, n = tenure in months
  All calculations use Decimal.js (20 significant digits, ROUND_HALF_UP).

FEES
  • Processing fee (% of principal)
  • Insurance fee (% of principal, optional)
  • Late fee per missed payment

DISBURSEMENT MODES
  BANK_TRANSFER | CHEQUE | CASH | MOBILE_MONEY

REPAYMENT MODES
  CASH | BANK_TRANSFER | CHEQUE | MOBILE_MONEY | POS | DIRECT_DEBIT

LOAN RESTRUCTURING
  Types: TENURE_CHANGE | RATE_CHANGE | PARTIAL_WRITE_OFF | COMBINED
  Requires approval workflow. Previous terms are snapshotted for audit.
  On approval, old schedule lines are marked SUPERSEDED and new schedule
  is generated from outstanding balance.

OWING BYPASS
  If a customer has an outstanding loan, new loan creation is normally
  blocked. A loan officer with appropriate permission can bypass this
  by providing a reason (owingBypass flag + owingBypassReason + linked
  loan IDs recorded on the application).

JOURNAL ENTRIES GENERATED
  • Disbursement: Dr Loan Receivable / Cr Cash/Bank
  • Repayment (principal): Dr Cash/Bank / Cr Loan Receivable
  • Repayment (interest): Dr Cash/Bank / Cr Interest Income
  • Fees: Dr Cash/Bank / Cr Fee Income
  • Write-off: Dr Bad Debt Expense / Cr Loan Receivable

8.4 SAVINGS MANAGEMENT
------------------------------------------------------------------------
Routes:  /savings                — Account list
         /savings/new            — Open new savings account
         /savings/[id]           — Account detail + transaction history
         /savings/withdrawals    — Withdrawal approval queue

Action:  src/actions/savings.actions.ts

SAVINGS TYPES
  DAILY    — Regular daily savings (field agents collect)
  TARGET   — Goal-based savings with target amount and date
  FIXED    — Fixed-term savings (not the same as Fixed Deposit)
  CORPORATE — Corporate savings accounts
  JUNIOR   — Under-18 savings
  CURRENT  — Current/transactional accounts

ACCOUNT BALANCE FIELDS
  currentBalance   — Actual balance
  availableBalance — Balance minus any holds
  holdAmount       — Amount temporarily held (pending withdrawals, etc.)

TRANSACTIONS
  Types: DEPOSIT | WITHDRAWAL | INTEREST_CREDIT | FEE_DEBIT |
         TRANSFER_IN | TRANSFER_OUT | REVERSAL | ADJUSTMENT
  Every transaction stores balanceBefore and balanceAfter for reconciliation.
  Transactions can be reversed (isReversed flag + reversalRef).

WITHDRAWAL WORKFLOW
  1. Teller/officer creates WithdrawalRequest.
  2. Request goes to queue (/savings/withdrawals).
  3. Authorised staff approves/rejects.
  4. On approval: actual SavingsTransaction is created and balance updated.
  Status: PENDING → APPROVED / REJECTED → PROCESSED

INTEREST ACCRUAL
  Handled by the daily cron job. Frequency configurable per product:
  DAILY | WEEKLY | MONTHLY | QUARTERLY | ANNUALLY.

CHART OF ACCOUNTS
  Hierarchical (parent/child via parentId + level).

  Normal balance: DEBIT (Assets, Expenses) or CREDIT (Liabilities,
  Equity, Income).
  System accounts (isSystemAccount=true) cannot be deleted.
  Header accounts (isHeader=true) are for grouping; cannot post to them.

DOUBLE-ENTRY ENGINE (accounting-engine.ts)
  createJournalEntry(params):
    1. Validates financial period is not HARD_CLOSE.
    2. Validates debits = credits (throws if unbalanced or zero-value).
    3. Validates all account IDs are active non-header accounts.
    4. Generates sequential entry number.
    5. Creates JournalEntry + JournalEntryLine records in a transaction.
    6. If autoPost=true, updates account currentBalance immediately.

  postJournalEntry(entryId, approvedById):
    Posts a DRAFT/APPROVED entry. Updates all account balances.

  reverseJournalEntry(entryId, reason, reversedById):
    Creates a reversal entry (debits ↔ credits swapped), auto-posts it,
    marks original as isReversed=true with reversal entry link.

  generateTrialBalance():
    Returns all non-zero leaf accounts with debit/credit classification
    and confirms total debits = total credits.

  closePeriod(year, month, closeType, closedById):
    SOFT_CLOSE allows adjustments; HARD_CLOSE is permanent.
    HARD_CLOSE cannot be reversed.

FINANCIAL PERIOD MANAGEMENT
  Periods must be explicitly opened/closed. Journal entries cannot be
  posted to a HARD_CLOSE period (validatePeriodOpen check).

ENTRY TYPES
  STANDARD | OPENING | CLOSING | ADJUSTMENT | REVERSAL | ACCRUAL | SYSTEM

15. KEY BUSINESS RULES & FINANCIAL LOGIC
================================================================================

LOAN CREATION RULES
  • Customer must be ACTIVE and KYC-verified
  • Loan amount must be within product min/max limits
  • Tenure must be within product min/max tenure
  • Customer cannot have an existing active loan unless owingBypass is used
  • Processing fee and insurance fee are calculated on principal amount

LOAN APPROVAL RULES
  • Approver's role.approvalLimit must be ≥ loan principalAmount
  • If amount exceeds manager limit → REFERRED_UP to higher authority
  • Multi-level approvals are tracked (LoanApproval.level)

SAVINGS WITHDRAWAL RULES
  • Withdrawal cannot exceed availableBalance (currentBalance - holdAmount)
  • Product may have maxDailyWithdrawal limit
  • Withdrawals above a threshold require approval workflow
  • WithdrawalRequest creates a hold on the account until processed/rejected

FIXED DEPOSIT RULES
  • Interest rate determined by FixedDepositRate table (tenure + amount band)
  • Premature closure incurs penalty (penaltyAmount calculated on accrued interest)
  • At maturity: rollover, payout, or transfer per maturityInstruction

ACCOUNTING RULES
  • All financial transactions MUST create balanced journal entries
  • Debits must exactly equal credits (validated before DB write)
  • Cannot post to HARD_CLOSE periods
  • Cannot post to header accounts (isHeader=true)
  • Account balances updated atomically within a Prisma transaction
  • Normal balance rules:
      Assets + Expenses: DEBIT increases, CREDIT decreases
      Liabilities + Equity + Income: CREDIT increases, DEBIT decreases

AUDIT RULES
  • Every login (successful and failed) is logged
  • Every CRUD operation on financial entities is logged
  • Old and new values are captured as JSON on UPDATE operations
  • Soft deletes (not hard deletes) are used to preserve audit trail
  • AuditLog table is append-only (no update/delete operations)

PASSWORD RULES
  • New accounts have mustChangePassword=true
  • After 5 failed logins, account is locked for 30 minutes
  • Password hashed with bcryptjs (min 12 rounds recommended)
  • Users are forced to /change-password if mustChangePassword=true

REFERENCE NUMBER FORMAT
  Generated by Sequence model: prefix + zero-padded counter
  Example sequences: LOAN (LN000001), CUSTOMER (CUS000001),
  SAVINGS (SAV000001), FD (FD000001), JOURNAL (JNL000001),
  RECEIPT (RCP000001), WITHDRAWAL (WDR000001)
